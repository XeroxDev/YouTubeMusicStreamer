# 1. Twitch Accounts, Authentication & Session Lifecycle

## Summary

The Twitch side of the app has been reworked to better match how streamers actually operate.
Instead of forcing one account to do everything, the app now supports a split model where the **Broadcaster Account** handles ownership, rewards, and privileged API interactions while a dedicated **Bot Account** can handle chat-facing responses.

This chapter covers the new multi-account model, improved login flows, independent account lifecycles, safer subscription ownership, token refresh hardening, and more reliable auth cancellation behavior.

## Why This Matters

For many streamers, using the broadcaster account for every single chat response is awkward.
It can clutter chat, blur responsibility boundaries, and create unnecessary friction when managing bot-style interactions.

This release introduces a cleaner model:

- your **bot identity** can respond in chat
- your **broadcaster identity** can remain focused on ownership, rewards, and API permissions
- both can now be managed more independently and more safely

The result is a setup that feels more professional, more flexible, and less brittle during long sessions.

## Headline Improvements Included

- Dedicated **Bot Account** support
- Clean fallback to broadcaster-only usage if no bot account is configured
- Independent account connection, disconnection, and switching behavior
- Safer and clearer browser-based auth flow
- Better differentiation between **real system errors** and **user-cancelled auth**
- Background token refresh hardening to reduce session expiry during long streams
- Selective EventSub cleanup so the app only manages subscriptions it actually owns
- More explicit Twitch session handling and state flow internally

## What Changed

### Dedicated Bot Identity

You can now connect a secondary Twitch account to act as a dedicated **Bot Account**.
That bot can handle command responses and confirmations while your broadcaster account remains the primary owner for stream-related permissions and reward interactions.

This removes the old "everything through the broadcaster" limitation and makes the system much more natural for channels that already separate on-stream identity from bot identity.

### Smart Fallback Behavior

The app does not force a two-account setup.
If you do not want a bot account, or simply have no need for one, the app can still operate using only the broadcaster account.

That means the new model is an upgrade in capability, not a hard requirement.

### Independent Login Lifecycles

Broadcaster and Bot sessions are no longer treated as one fused, restart-sensitive blob.
They can now be connected, disconnected, and switched more independently.

This matters for real usage because it lets you:

- re-auth one side without tearing down the other
- swap bot accounts without rebuilding your whole session
- recover more gracefully from partial auth problems

## What Users Will Notice

- Chat responses can now come from a proper bot identity instead of the broadcaster account
- Broadcaster chat stays cleaner and less noisy
- Account switching is less disruptive
- Logging in feels safer and less awkward because the flow now uses the system browser
- Closing the browser during auth no longer looks like a catastrophic failure if it was simply a user cancellation

## Observable System Behavior

### System Browser Authentication

Login is now performed through the **system browser** rather than relying on an embedded browser window.

This improves both usability and security posture:

- users interact with a familiar browser session
- auth windows are less likely to get "stuck" in awkward embedded states
- the flow aligns better with modern OAuth expectations

### Cancellation Awareness

If a user closes the auth window, the app now treats that specifically as **user cancellation** rather than misclassifying it as a generic system failure.

That sounds small, but it significantly improves supportability and reduces confusing false-error reporting.

### Background Token Refresh Hardening

The Twitch integration previously had a refresh weakness where long-running sessions could end up expiring if background refresh behavior did not sustain the session correctly.

That background refresh behavior has been fixed and hardened so that long streams are less likely to silently drift into expired or broken auth states.

### EventSub Ownership Safety

The app now only cleans up **the EventSub subscriptions it created itself**.
It no longer risks "nuking" unrelated Twitch integrations created by other stream tools.

This is one of the most important Twitch reliability changes in the release because it prevents collateral damage outside the app’s own ownership boundary.

## Reliability, Failure Handling & Edge Cases

### Partial Account Recovery

Because Broadcaster and Bot are more explicitly modeled, partial failures are easier to reason about and recover from.
A broken bot session no longer has to mean that the broadcaster session becomes unusable or vice versa.

### Safer Auth Failure Reporting

The app now distinguishes between:

- intentional auth cancellation
- genuine auth or browser errors
- broader session or token problems

That distinction improves both user trust and support workflows.

### Long-Session Stability

Background token refresh hardening directly targets the kind of failure that only appears during long stream sessions.
This is the type of issue that can make software feel unreliable even if everything worked initially.

### Subscription Boundary Respect

Selective subscription cleanup prevents the app from stepping outside its own responsibility and breaking other tools that also use Twitch integrations.

## Technical Implementation

### Composite Session Model

The Twitch subsystem has been rebuilt around a more explicit internal model that can manage independent **Broadcaster** and **Bot** sessions.
In the "Refactor" version, this is described as a composite Twitch session/state-machine style design that tracks the separate account roles more deliberately.

This is a substantial upgrade over a looser "single session that does everything" approach.

### Explicit Ownership & State Flow

Rather than hiding behavior behind ad-hoc implicit coupling, the release moves Twitch account handling toward:

- explicit ownership
- more isolated lifecycle management
- clearer result handling
- safer cleanup boundaries

This is important because Twitch issues often involve timing, auth state, and external resources, all of which benefit from explicit modeling.

### Reward and Session Interoperability

The Twitch account model also supports the reward automation improvements described in the next chapter.
Broadcaster and Bot responsibilities can now be separated more cleanly in a way that fits actual Twitch usage patterns.

## Verification & Confidence Signals

Relevant verification themes in this release include:

- broad xUnit coverage for state transitions and orchestration logic
- seam injection around platform boundaries for deterministic testing
- stricter PR validation so auth and orchestration regressions are less likely to slip through
- final verification snapshots indicating roughly **527 tests passed**, **0 warnings**, and **0 errors** in validated builds

### Changed

- EventSub cleanup is now ownership-aware

### Hardened

- Long-session stability
- Partial session recovery paths
- State ownership boundaries

# 2. Rewards, Redemptions & No-Touch Moderation

## Summary

The app now takes over the lifecycle of integrated Twitch song request rewards in a much more complete and deterministic way.
This is not just a minor convenience feature. It changes how reward-backed song requests are moderated, reported, and resolved.

Instead of leaving the streamer or moderator to manually inspect and clean up reward states, the app can now automatically decide what to do when a request succeeds or fails, then push the correct lifecycle result back into Twitch.

## Why This Matters

Manual reward moderation is one of the easiest ways for a stream tool to feel annoying in daily use.
Even when the core feature technically works, the surrounding workflow can still be bad if users must constantly approve, reject, refund, and investigate things by hand.

This release reduces that overhead significantly.

It turns the reward flow into something closer to a fully-managed system:

- accepted requests are fulfilled automatically
- failed requests are refunded automatically
- incompatible rewards can be diagnosed more clearly
- moderators do less repetitive cleanup work

## Headline Improvements Included

- Full app-managed reward lifecycle
- Automatic reward refunding when requests fail
- Automatic reward fulfillment when requests succeed
- Clearer compatibility and configuration diagnostics for rewards
- One-click fixes for certain reward compatibility issues
- Richer failure reason handling through typed result outcomes

## What Changed

### No-Touch Reward Moderation

The app now manages the full lifecycle of integrated reward-backed song requests rather than acting as a passive trigger that leaves the rest of the cleanup work to the streamer.

This is one of the most user-visible quality improvements in the release.

### Auto-Refund on Failure

If a request cannot be accepted, the app automatically refunds the viewer’s Channel Points.

Common failure paths include:

- queue full
- blacklisted song
- disabled command
- incompatible reward setup
- invalid or missing required input

Instead of leaving the user’s points stuck in a bad state or forcing manual moderator intervention, the app resolves the failure path immediately.

### Auto-Approve on Success

When a song request succeeds, the app can now automatically mark the redemption as **Fulfilled** in Twitch.

That removes the need for someone to manually clean up reward state after a successful request.

### Reward Compatibility Tracking

The app can now explain **why** a reward is incompatible or broken.
For example, if a reward is missing a required configuration such as expected user input behavior, the app can expose that reason more clearly.

In the more feature-rich variants of the release notes, this is paired with a one-click **Fix** flow for certain compatibility issues.

## What Users Will Notice

- Far less manual reward queue maintenance
- Failed requests do not silently consume viewer points without resolution
- Successful requests no longer require routine manual fulfillment cleanup
- Broken or misconfigured rewards are easier to identify
- The reward experience feels much more intentional and professional

## Observable System Behavior

### Deterministic Reward Outcomes

The reward system now reacts to the actual result of request processing rather than treating everything as a vague success/failure blob.

That means:

- valid accepted requests move toward fulfillment
- invalid or rejected requests move toward refund logic
- compatibility problems are surfaced with more context

### Faster Resolution of Failure Paths

Before, some failure outcomes could leave the streamer or moderator to interpret what went wrong and decide how to resolve the Twitch-side state.
Now, the app resolves much more of that behavior directly.

### Better Surface for Support and Diagnosis

If a reward is broken or misconfigured, the app has better ways to report that state, making support and troubleshooting more straightforward.

## Reliability, Failure Handling & Edge Cases

### Queue Full and Command Disabled Cases

These are classic frustration points in stream tools.
The new reward handling ensures these cases lead to a clear, recoverable, and user-respecting outcome rather than a confusing half-failed redemption.

### Blacklist and Validation Rejections

If a song is blacklisted or invalid, the system now has a more structured way to reject the request and refund the associated reward redemption.

### Reduced Manual Moderation Drift

When manual moderation is required for too many "normal" cases, inconsistent behavior tends to emerge. Some redemptions get forgotten, some get handled late, and some get handled inconsistently.

Automating the reward lifecycle reduces that drift.

## Technical Implementation

### Typed Result Pipeline

A major enabling change in this release is the shift from plain boolean outcomes to a richer **`CommandResult`** model with explicit reason codes and related data.

This matters because reward automation depends on understanding **why** a request failed, not just that it failed.

A boolean can tell you almost nothing.
A typed result can tell you whether the rejection was due to:

- cooldown
- validation failure
- blacklist match
- queue limits
- disabled command
- or another explicit reason

That richer outcome model makes deterministic reward lifecycle behavior possible.

### Reward Logic Built on Structured Outcomes

By using structured command results, the reward subsystem can make much more reliable decisions about whether to:

- approve/fulfill
- reject/refund
- explain incompatibility
- prompt repair/fix flow

This turns reward handling into a more formal orchestration layer instead of a bundle of special cases.

## Verification & Confidence Signals

The release variants highlight improved automated testing and state transition coverage in the broader command/runtime layer, which directly benefits reward reliability.
A system that uses explicit outcomes and deterministic transitions is much easier to test than one based on loosely-coupled booleans and side effects.

## Improvement Index

### Added

- App-managed reward lifecycle
- Auto-refund on failure
- Auto-fulfill on success
- Compatibility tracking and explanation
- One-click reward fix flow in supported cases

### Changed

- Reward handling is now driven by richer outcome information
- Moderation workload shifts from human cleanup to deterministic app behavior

### Fixed

- Manual moderation gaps around successful and failed reward flows
- Cases where a redemption could end in an unclear or inconsistent state

### Hardened

- Reward processing against common validation and queue failure paths
- Supportability of broken reward configurations

# 3. Startup, Recovery, Multi-Instance Handling & Launch Reliability

## Summary

Startup behavior has been substantially overhauled.
This release replaces a more opaque, fragile startup path with a phased, validated startup model that exposes progress, supports health checks, handles stale instances more safely, and uses a proper inter-process control channel for multi-instance behavior.

This is one of the most trust-building parts of the release because startup failures are among the most visible quality problems users experience.

## Why This Matters

Nothing makes a desktop app feel broken faster than any combination of the following:

- the app "starts" but never appears
- an old hidden process blocks a new launch
- a second launch does nothing meaningful
- the user cannot tell whether the app is loading, hung, or dead
- critical startup dependencies fail silently

This release attacks those problems directly.

## Headline Improvements Included

- Explicit phased boot sequence
- Live phased health/progress visibility
- Named-pipe instance control channel
- Stale instance/zombie process detection and recovery
- Better bring-to-front behavior for already-running instances
- Startup validation and dependency probing during boot
- Safer failure boundaries between startup phases

## What Changed

### Phased Boot Sequence

Startup now runs in distinct phases rather than feeling like a black box.
Across the release variants, this phase model is described as:

- Bootstrap
- Settings
- Core
- Window
- Subsystems

This makes startup easier to reason about internally and easier to observe externally.

### Health Indicators During Startup

Users can now see startup progress and subsystem health more clearly instead of being left guessing whether the app is stuck.

This matters because "no visible window yet" is very different from "the app is dead," but many desktop apps fail to communicate that distinction.

### Smart Bring-to-Front Behavior

If the app is already running, launching it again now reliably signals the existing instance and brings it forward, even when minimized or hidden.

This removes a class of annoying behavior where users launch the app repeatedly because nothing visible happened.

### Stale Instance Recovery

If the app previously crashed or left behind an invalid stale process state, the next launch can now detect and recover from that situation more gracefully.

This is described in the source variants as recovery from "stale instances" or "zombie processes."

## What Users Will Notice

- Fewer "ghost starts" where the app seems to hang invisibly
- Better startup transparency
- A second launch behaves like a restore/bring-to-front command instead of feeling broken
- Crashes and improper prior shutdowns are less likely to poison the next startup

## Observable System Behavior

### Five-Phase Startup Validation

Startup is now structured into explicit phases with validation/health logic at each step.
This creates cleaner dependency ordering and reduces the risk of unclear constructor-driven side effects causing strange startup failures.

### Secure Inter-Process Signaling

Secondary launches now communicate with the primary instance through a **named pipe** rather than brittle window-finding logic.

That is a significant technical and practical reliability improvement.

### Endpoint Probing Before Auth/Attach

Before attempting certain subsystem interactions, such as YTMDesktop auth/connect behavior, the app can now probe the relevant endpoint to confirm that the correct application is actually listening.

That prevents an entire class of "wrong thing on the same port" failures.

## Reliability, Failure Handling & Edge Cases

### Hidden Window / Tray / Minimized States

Already-running instances may be hidden or minimized in ways that make them look absent to the user.
The new bring-to-front behavior specifically targets those states so the app behaves predictably.

### Post-Crash Recovery

Old stale state after a crash is one of the easiest ways for an app to feel unreliable on the next launch.
The new recovery logic helps prevent startup from being blocked by a dead or invalid leftover instance.

### Phase Isolation

Explicit startup phases make it easier to identify where a failure occurs and to keep unrelated startup work from collapsing into one opaque failure blob.

## Technical Implementation

### `IStartupCoordinator` and Explicit Startup Orchestration

The refactor-oriented variants describe startup moving away from constructor-driven side effects and toward an explicit startup orchestration model, centered around a startup coordinator abstraction.

This is a strong architectural improvement because startup is one of the worst places to rely on accidental side effects.

### Named-Pipe IPC

Multi-instance behavior now uses a named-pipe control path.
That is more deterministic, more secure, and less brittle than trying to locate and manipulate windows directly.

### Health-Checked Boot Lifecycle

The phased startup model also creates a clearer place for subsystem validation and health reporting, which helps both users and developers understand what the app is doing during launch.

## Verification & Confidence Signals

- startup behavior now lives in a more explicit orchestration model that is easier to test deterministically
- seams around platform interactions improve validation of launch and process state logic
- final build verification remained clean across validated release snapshots

## Improvement Index

### Added

- Explicit phased startup system
- Startup health visibility
- Named-pipe control channel
- Stale instance recovery logic
- Pre-auth endpoint probing

### Changed

- Secondary launch now behaves as controlled signaling to the primary instance
- Startup is more observable and structurally ordered

### Fixed

- Ghost-start / hidden-start style behavior
- Brittle bring-to-front handling
- Startup failures caused by stale background state
- Startup failure when the `AppData` folder is missing

### Hardened

- Crash recovery
- Multi-instance handling
- Dependency validation during startup

# 4. YouTube Integration, Queueing & Playback Guarantees

## Summary

The YouTube and queueing side of the app has been reworked to be more deterministic, more resilient to lag and malformed input, and less likely to lose track of what is actually happening in the player.

This chapter covers queue progression guarantees, metadata handling, URL parsing hardening, request validation, and improvements that reduce invisible playback-related desync.

## Why This Matters

Queue bugs are extremely visible during live use.
If a song disappears too early, the wrong item is removed, a malformed URL behaves strangely, or the app trusts a state change that never really happened, users notice immediately.

For a music-related stream tool, this is core quality, not polish.

## Headline Improvements Included

- Confirmation-based queue advancement
- Safer queue auto-advance behavior
- Metadata resolution improvements
- Centralized/shared YouTube validation workflow
- Hostile URL parser hardening
- Better blacklist precision and validation behavior
- Reduced risk of lost songs during lag or desync

## What Changed

### Pending-Target / Player Confirmation Before Removal

One of the most important queue changes is that the app no longer blindly removes an item from the queue just because it *thinks* the next song should have advanced.

Instead, the queue now waits for the player to confirm the target change.
Across the variants, this is described as waiting for the YouTube Music player to confirm the next song has started, or waiting for the player to emit a matching Video ID before completing a removal.

This directly reduces the risk of "lost songs" caused by race conditions or lag.

### Metadata Resolver Separation

Metadata fetching has been isolated or separated more clearly from other processing responsibilities.

That helps make lookup behavior faster, cleaner, and more reliable, especially in flows where validation and metadata retrieval previously risked becoming entangled.

### Unified YouTube Workflow

The refactor-oriented material describes a centralized/shared service for YouTube-related validation, metadata fetching, URL handling, and blacklist checks.

This is important because a unified path reduces drift between commands that otherwise might each implement slightly different logic.

## What Users Will Notice

- Fewer cases where songs appear to vanish from the queue incorrectly
- More trustworthy behavior during laggy transitions
- Better behavior when pasting messy or malformed YouTube URLs
- More consistent validation outcomes across YouTube-related commands

## Observable System Behavior

### Queue Items Are Removed Later, but More Safely

The queue system now behaves more conservatively.
Rather than assuming the player successfully moved forward, it waits for confirming evidence.

That means progression may be slightly more formal internally, but the overall user experience is safer because false advancement is reduced.

### YouTube URLs Are Parsed More Defensively

The URL parser now handles:

- multiple `?v=` parameters
- encoded characters
- pathological trailing slashes
- more hostile or malformed URL patterns

That matters because user input on live streams is often messier than idealized test input.

### Validation and Metadata Logic Are More Consistent

By centralizing the flow and separating metadata responsibilities more cleanly, the app reduces the risk of inconsistent behavior between commands that all accept YouTube content.

## Reliability, Failure Handling & Edge Cases

### Lag and Desync

Lag is one of the most dangerous sources of queue corruption because it creates false assumptions about what the player is actually doing.
The confirmation-based progression logic directly targets this.

### Hostile and Pathological Input

A live command environment invites malformed URLs, weird whitespace, duplicate parameters, and awkward pasted data.
The parser hardening in this release targets precisely those kinds of cases.

### Shared Validation Paths

A centralized validation flow is also a reliability improvement because it avoids "this command accepted it but that command rejected it" inconsistencies.

## Technical Implementation

### Centralized URL / Metadata / Blacklist Workflow

The release notes describe a unified YouTube workflow that centralizes URL validation, metadata resolution, and blacklist checking into a shared service used by multiple commands.

This is a good structural change because it:

- reduces code duplication
- improves consistency
- makes behavior easier to test
- makes fixes apply more broadly across the command surface

### Queue Logic Based on Explicit Confirmation

The queue progression model is now built around a stricter confirmation step instead of overly-optimistic assumptions.
That directly addresses race-condition-style problems in player coordination.

## Verification & Confidence Signals

- URL logic is explicitly covered by the expanded xUnit test suite
- state transitions and parsing are called out as covered areas
- hostile input testing includes large malformed and pathological values

## Improvement Index

### Added

- Confirmation-based queue advancement
- Cleaner metadata separation
- Shared YouTube workflow/service model

### Changed

- Queue removal now waits for player confirmation
- Validation behavior is more centralized and consistent

### Fixed

- YouTube URL parser returning comma-separated IDs for duplicate query parameters
- Lost-song style behavior during lag or premature queue advancement
- Duplicate/awkward URL patterns breaking parsing

### Hardened

- Desync handling
- URL parsing under malformed input
- Cross-command consistency for YouTube validation logic

# 5. Widget Server, Audio Pipeline & Overlay Stability

## Summary

The widget and audio visualization side of the app has been upgraded to behave more like an independent subsystem rather than a fragile extension of the player.
Widgets now stay online even when YouTube Music is closed, audio device changes can apply more cleanly, and visualizers now recover/settle more correctly when music stops.

This chapter covers overlay stability, widget independence, audio device switching, visualizer reset behavior, and related persistence/config coordination.

## Why This Matters

For stream-facing software, broken overlays are highly visible.
A visualizer that freezes, a browser source that disconnects when the music app closes, or a widget server that keeps stale device/port state immediately makes the product feel untrustworthy.

This release puts serious work into making widgets feel like stable presentation surfaces rather than fragile side effects.

## Headline Improvements Included

- Independent widget server behavior
- Professional "Waiting for Music" idle state
- Instant audio device switching
- Zero-audio frame injection on stop
- Cleaner visualizer resets
- Better coordination between settings changes and active widget behavior

## What Changed

### Independent Widget Server

Your browser-source widgets now stay connected and active even if YouTube Music is closed.
Instead of collapsing into a broken connection state, they remain alive and present a cleaner idle experience.

This is a substantial UX improvement because overlays no longer feel tied to the lifetime of the player window/process in such a brittle way.

### Waiting-for-Music State

Rather than showing an ugly failure state or broken source behavior, widgets can now present a friendly **"Waiting for Music"** message when playback is unavailable.

That creates a more professional on-stream presentation and makes idle periods look intentional rather than broken.

### Instant Audio Switching

Changing the audio capture device in settings now updates the widget server more immediately.
In practical terms, this means changing headsets or capture devices does not require so much restart-heavy recovery just to get visualizers working again.

### Clean Visualizer Resets

When playback stops, visualizers now settle back to zero instead of freezing on the final audio frame.

This sounds small, but visually it makes a major difference.
A frozen last-frame visualizer looks broken.
A clean return to zero looks intentional.

## What Users Will Notice

- Overlays stay alive when the music app is closed
- Idle overlays look deliberate instead of broken
- Audio device changes are less disruptive
- Visualizers stop gracefully instead of freezing visually

## Observable System Behavior

### Silence / Zero-Audio Frame Injection

When music stops, the app now pushes a final zero-audio frame to the widget server so downstream clients can flush their buffers and settle correctly.

This is the concrete behavior behind the improved visualizer reset experience.

### Widget Independence from Player Lifetime

Widgets now behave more like standalone presentation endpoints that can wait for audio/music state instead of dying when the player disappears.

### Better Runtime Reaction to Settings Changes

Changes such as audio device adjustments or related widget settings now apply more directly to the running subsystem rather than being trapped behind a full restart requirement.

## Reliability, Failure Handling & Edge Cases

### Device Changes Mid-Session

Changing headsets or capture devices during use is a realistic scenario.
The new behavior reduces the chance that the widget/visualizer side gets stuck in a stale state after a device swap.

### Idle Player State

When the music source is absent, the system now has a valid, user-friendly idle state instead of behaving like it is disconnected or broken.

### Client Buffer Cleanup

The zero-frame injection specifically addresses downstream/client-side cases where the last audio state could otherwise remain visually stuck.

## Technical Implementation

### Explicit Stop-State Signaling

The "silence frame injection" described in the release notes is a good example of converting an implicit absence into an explicit state signal.
Rather than simply stopping audio updates and hoping clients infer the right outcome, the system emits a final zero state.

### Widget Server as a More Independent Subsystem

Architecturally, the widget server is now treated more like its own runtime component with clearer lifecycle behavior rather than a purely dependent sidecar.

### Runtime Device Rebinding / Settings Coordination

The improved headset/device switching behavior implies better runtime coordination between settings, active capture state, and the widget/audio pipeline.

## Verification & Confidence Signals

While the source material does not isolate widget tests into a separate published count, this chapter benefits from:

- improved orchestration and seam injection around runtime services
- better explicit state behavior that is easier to validate
- general build/test hardening across the release

# 6. Settings, Persistence, Migration & Data Integrity

## Summary

The app’s persistence layer has been fundamentally upgraded from fragile file-based configuration toward a more robust SQLite-backed model with transactional writes, safer migration behavior, archive handling for legacy data, and more immediate runtime application of many settings.

This chapter covers the persistence overhaul, automatic migration, safe archival, corrupt config handling, transactional saves, and settings/runtime application improvements.

## Why This Matters

Configuration and queue persistence problems are some of the most damaging issues in desktop software because they erode trust silently:

- data gets half-saved
- queue order is lost
- configs become corrupt
- runtime changes do not actually apply
- users become afraid to change settings because recovery is unclear

This release addresses those concerns at the storage and state-management level.

## Headline Improvements Included

- SQLite-based persistence replacing fragile text files
- Automatic JSON-to-SQLite migration for existing users
- Archive and invalid-data handling for legacy settings files
- Transactional database writes for settings, queue, and blacklist data
- Instant application of many settings after saving
- Safer corrupt config recovery paths

## What Changed

### SQLite Replaces Fragile Text Files

The persistence model has been moved away from fragile text/config files and toward an **SQLite** database.

This is one of the biggest foundational changes in the release.
It upgrades storage from a loosely-managed file model into something much better suited for durability and structured state management.

### Automatic Migration for Existing Users

Existing file-based settings are migrated forward automatically.
This migration is designed to be a one-time, silent process for users rather than a manual conversion burden.

### Legacy Archive Handling

Successful legacy `AppSettings.json` migrations are archived rather than simply discarded.
Malformed or invalid legacy files are moved into a dedicated invalid/safety path instead of being allowed to silently poison startup.

Across the source versions this is described using folders such as:

- `backups`
- `invalid`
- legacy archive/safety folders

### Transactional Saves

Writes to important persisted state are now atomic/transactional.
This applies to core persisted data such as:

- settings
- queue
- blacklist

# 7. Commands, Parsing, Validation & Result Handling

## Summary

The command runtime has been substantially redesigned to be more explicit, more testable, and more resilient against malformed input and ambiguous outcomes.
This includes changes to how commands are activated, how results are represented, how YouTube-related workflows are shared, and how parsers behave under extreme or hostile input.

## Why This Matters

Command systems are one of the highest-risk parts of this kind of application because they are fed by unpredictable real-world chat/user input.
If parsing is weak, validation is inconsistent, or execution results are too vague, the whole feature surface becomes fragile.

This release strengthens the command layer both architecturally and behaviorally.

## Headline Improvements Included

- Transient command module activation
- Narrow command execution context
- Rich `CommandResult` typed outcomes
- Deterministic command discovery and validation
- Shared YouTube workflow for multiple commands
- Hardened argument parsing under hostile input
- Better failure reasons surfaced to users/support

## What Changed

### Transient Command Modules

Commands are no longer treated as long-lived singletons.
Instead, they are activated as transient modules per execution and receive a narrower, more explicit command context.

This reduces hidden shared state and improves both testability and runtime hygiene.

### Typed Result Pipeline

The app no longer relies on plain `bool` returns for command outcomes.
Instead, command execution can return a richer **`CommandResult`** carrying explicit reasons and placeholder/result data.

This is a foundational improvement because it allows other systems to behave intelligently based on *why* something happened.

### Deterministic Discovery & Validation

Command discovery is now more deliberate and validated.
Malformed command signatures are intended to fail loudly during startup in development rather than silently producing vague runtime weirdness.

### Shared YouTube Command Workflow

Multiple YouTube-related commands now run through shared validation and metadata logic instead of each command doing slightly different versions of the same thing.

## What Users Will Notice

- Command failures are less silent and more explainable
- Some failure messages can now be more specific
- YouTube-related command behavior is more consistent
- Edge-case input is less likely to break command handling

## Observable System Behavior

### Actionable Failure Reasons

Instead of just "nothing happened," the app can now surface more actionable reasons for failures, such as:

- user is on cooldown
- song is blacklisted
- queue is full
- command is disabled

This is a major support and UX improvement.

### Parser Resilience Under Hostile Input

The parser was rewritten or hardened to withstand:

- quote bombing
- 10k-character strings
- massive/unbalanced whitespace
- empty quotes such as `""`

That kind of hardening matters because chat input can be adversarial, accidental, or simply messy.

## Reliability, Failure Handling & Edge Cases

### Pathological Input

The release explicitly calls out pathological input handling.
This is important because parser failures often become app-wide quality problems if not contained.

### Duplicate Command Response Edge Case

A rare case where a single command could send two identical responses when a user both cheered and chatted simultaneously was fixed.

### Empty Quote Handling

The argument parser now correctly supports empty quoted arguments.
This is a subtle but correctness-oriented improvement that matters for predictable parsing behavior.

## Technical Implementation

### CommandContext and Execution Isolation

A narrower command context reduces accidental dependency sprawl and makes command execution easier to reason about in tests and code review.

### `CommandResult` as a Cross-Cutting Enabler

The typed result pipeline is not just a command-layer nicety.
It enables:

- deterministic reward handling
- better diagnostics
- cleaner UI/support explanations
- richer orchestration logic

### Reflective Discovery with Validation

Runtime command discovery and validation at startup can catch malformed command definitions earlier, especially in dev/test environments.

## Verification & Confidence Signals

# 9. Architecture, Dependency Injection & Engineering Standards

## Summary

This release is not only a feature update. It is also a significant architectural cleanup and modernization pass.
Static/global utility buckets were removed, UI logic was refactored behind facades, startup became explicit rather than side-effect-driven, platform boundaries were abstracted behind seams, and command/runtime behavior was made more formal.

This chapter gathers the architecture work that supports the visible improvements elsewhere.

## Why This Matters

Architectural work is often invisible until something breaks.
But much of the reliability and feature quality in this release exists **because** the codebase became more explicit, less globally coupled, and easier to verify.

This is the kind of work that converts a tool from "works most of the time" into "can evolve without collapsing under its own complexity."

## Headline Improvements Included

- Removal of static/global "god object" style utilities
- Stronger dependency injection boundaries
- Facade pattern between UI and core services
- Explicit startup orchestration model
- Better ownership and lifecycle modeling
- Platform seams for deterministic tests
- More formal command execution/runtime structure

## What Changed

### Static-Global Removal

The release notes call out the removal of `AppUtils` and similar static/global utility patterns.
These had acted as broad grab-bags or "god objects."

Their removal is a major structural improvement because static/global state often hides dependencies, encourages coupling, and complicates testing.

### Facade Pattern Adoption

UI components/pages no longer talk directly to deep core services as freely.
Instead, dedicated facades such as the following are used to mediate UI logic:

- `YtmDesktopFacade`
- `QueuePageFacade`
- `TwitchRewardsFacade`
- `LogViewerFacade`

This improves separation of concerns and makes page behavior easier to reason about.

### Explicit Startup Orchestration

Constructor-driven startup side effects were replaced with a more explicit startup coordinator model.

This is one of the highest-value architectural improvements because startup side effects are notoriously hard to debug and test.

### Seams Around OS / Platform Boundaries

Critical boundaries such as:

- Process
- FileSystem
- SecureStorage

are now behind interfaces, enabling deterministic orchestration tests and reducing direct hard coupling to environment APIs.

## What Developers Will Notice

- Dependencies are easier to trace
- UI responsibilities are cleaner
- Testing orchestration no longer requires as much environmental fakery or instability
- Cross-cutting services are less likely to sprawl into unrelated code paths

## Observable System Behavior

Most users will not see this chapter directly, but they experience it indirectly through:

- cleaner startup behavior
- better recovery logic
- more deterministic command handling
- stronger diagnostic surfaces
- safer persistence transitions

## Reliability, Failure Handling & Edge Cases

### Hidden Side Effects Reduced

Removing constructor-driven and static-global behavior reduces the chance that unrelated changes accidentally alter startup or subsystem state.

### More Testable Boundaries

Interface seams and explicit ownership models make it easier to simulate failures and verify orchestration logic.

### Better Lifetime Modeling

Transient command modules and clearer subsystem ownership reduce lifetime-related leaks and shared-state bugs.

## Technical Implementation

### DI-First Core

This release pushes the app toward a more consistent dependency-injected core rather than a mix of DI and ad-hoc static access.

### Facades as UI Boundary Layer

Facades now act as the intended bridge between UI and lower-level orchestration/services.
That centralizes page-specific logic and reduces direct entanglement.

### Explicit Ownership and Narrower Contexts

Across the release, many improvements point in the same architectural direction:

- narrower contexts
- explicit ownership
- clear lifecycle boundaries
- less hidden state

## Verification & Confidence Signals

This chapter is tightly coupled to the QA chapter because architecture and testability improved together.
The move toward seams, facades, explicit startup coordination, and typed outcomes directly supports deterministic automated testing.
